# Qoder-Versus-CodeBudy

当前阶段 2 家智能代理之间的对比，个人观点仅供参考，不代表以后

## 对比最终总结

| 对比项        | 胜出者     | 优势                                                        |
|--------------|-----------|------------------------------------------------------------|
| 综合能力      | CodeBuddy | 易用性：可直接复制为 MarkDown 文本，网络连接稳定；复杂问题处理能力强 |
| 准确性与还原度 | Qoder     | 终于原始要求，对于不合理的问题，会主动问用户是否要求调整，不会擅自修改 |
| 安全性        | Qoder     | 执行所有脚本都会要求用户确认，代价是不便捷，速度慢                  |
| 便捷性        | CodeBuddy | 除非是需要管理员权限、删除操作的脚本才需要用户确认                 |

## 提问

### 确保提问的公平性

- **对比模型**：确保使用同一模型 **DeepSeek-V4**
- **问题提问的时间和方式**：3 个问题都在最近的时间内完成，每次提问必须近乎是同一时间对 2 个智能体提相同问题

### 具体问题

- **日常开发问题**：某个 C# 项目里面，支持 UI 界面国际化（实际测试过，公司项目源码不能透露）
- **网上教程不完整的问题**：要求使用 msvc++ 编译器编译 FFmpeg 音频解码库并做定制（没有用编译的库做验证，只观察实际步骤和效果）
- **综合性复杂工程问题**：plan 模式下，要求使用 C++ DirectX 转写 Python 游戏坦克大战

## 实际表现

- 综合能力 **CodeBuddy** 更好，但是它的**每次回答需要人去认真核实检查**，有的时候会自主告诉你他觉得方案哪方面不好，按照它的想法修改
- Qoder 的**准确性是依托于自主帮你写测试代码、跑验证、分析测试框架输出或者抓图像素对比保证的**，这导致了更多的 token 消耗、更容易钻牛角尖，即触发大模型的死循环，强行终止会导致无法一键完整复制所有回答，只能逐段复制，因此这个智能体是基于 **Looping Engineer**
- 除了第 1 个问题牵涉到公司项目源码，不能泄露具体问答细节和源码，只能给简要结论和智能体思路对比，其他会在对应目录里面，给出具体问答过程

### 日常开发问题：UI 界面国际化

1. **问题背景**：本次没有提供贴图资源，应当准备好贴图资源，再来一次对比测试
2. **问题描述**：整个开发需要使用 C# 和 DevExpress，我需要在软件设置页面里面，添加一个菜单“语言设置”，菜单文字前面要有 Language 的图标，这个菜单悬停后会展开一个二级菜单，二级菜单分别是“简体中文”、“English”，同样的是二级菜单的文字前面要有对应国家的国旗，区别是二级菜单本质上是互斥的 RadioButton，默认要确保“简体中文”是选中的，但是如果程序有配置文件的情况下，需要读取配置文件里面的语言选项（某个属性），从而初始化设置为这个语言并加载对应资源。需要考虑切换的处理
3. **问题潜在难点**：
  - 没有提供国旗图像资源
  - 应用程序切换语言意味着默认需要重启 App，因为操作系统早期设计的时候没有考虑过国际化
4. **个人预期与实际表现**：
  - Language 图标处理：
    - 预期：智能体应当能在 **DevExpress** 安装目录下找到对应图片资源，不需要人工提醒
    - 表现：**仅 Qoder 做到**，CodeBuddy 是不是打算程序自绘这点我没留意
  - 国旗图标处理：
    - 预期：智能体应当自主下载统一的、对应的国旗图标，且需要考虑版权、图片有无水印、图片质量和尺寸的统一
    - 表现：Qoder **连续 3 次自主生成国旗图标**，并修改美国星条旗的星星到比较好的水平，但是**中国国旗的五角星有一个错位的**，实际上**星星是方块像素点，16x16 的图片看不明显**；CodeBuddy 居然尝试**用 C# code-behind 代码画国旗**，导致代码无法编译通过
  - 应用程序重启处理预期：
    - 预期：先分派延迟启动进程任务，再正确处理应用程序退出与资源释放
    - 表现：代码层面上，2 者无明显差异，但是 **CodeBuddy** 因为自绘问题，无法编译通过所以无法验证

### 网上教程不完整的问题

1. **问题背景**：本次任务降低了难度：没有要求支持**汇编语言**优化，没有要求使用 **msvc++** 特有编译优化指令（一旦使用，大概率 2 个智能体都会失败），且这部分网上教程极少，依赖于尝试、比较并整合微软与 GNU 编译指令文档，这部分属于较高难度；**此外，在 26 年 6 月之前，CodeBuddy 根本无法正确给出我需要的这个解答**，本次回答内容和我以前的做法很类似，大概率是有人喂了我的文档
2. **问题描述**：请你在桌面建立一个 FFmpeg-CodeBuddy 目录，你要做的是：1. 将官方 FFmpeg v4.4.2 的版本下载到这个目录下；2. 必须是使用 msvc++ 编译器编译 FFmpeg 库；3. 要求 FFmpeg 只编译编解码库，且只支持 mp3、sbc、wav、pcm 这些格式；我需要编译出来的 .lib 和 .dll 来实现相关功能
3. **问题潜在难点**：
  - 预料教程本身存在不足或错误：关于编译 Windows 版本的音视频处理库，网络上的教程即便是官网都不全，还有一堆错误的
  - 该任务考察智能体复杂任务规划和工作流编排问题：不少依赖外部工具，下载、设计、计划、编译、验证整个工作流如何规划
  - 实际验证难题：很多时候看起来是编译好了，实际验证发现不能跑，只有做过音视频处理相关的人，能察觉到这里面的问题
4. **个人预期与实际表现**：
  - 外部依赖工具下载：
    - 预期：网上大量的教程和语料库训练，智能体应该都能知道任务开始之前，需要下载到对应的工具，但工具安装需要**管理员权限**，理论上失败
    - 表现：2 家都成功下载了对应工具，并且居然在用户同意下都安装成功
    - 结论：说明智能体已经默认拥有了**管理员权限**，所以开发过程中，对于不确定的和可能存在风险的命令脚本，人有审查规避的义务；此外为了避免复杂任务出错，**使用智能体辅助编程**应该平衡好**生成代码量和审核代码量**的差异，防止**“生成半小时，修改两三天”**这种悲剧发生
  - 能够编译出符合交付要求的库：
    - 预期：理论上大概率都失败，使用 **msvc++** 编译 **Windows** 版本的库，网络上即便是官方教程也极少，即便编译出来，很多也不是使用正统的方式，而是搭建 **Windows** 内模拟 **Linux** 的编译系统，然后完成。只要是这种方法的，一律判定为失败
    - 表现：2 家水平相当，相对而言，Qoder 轻微胜出，考虑到了 pcm 编码有多种
  - 能够正确验证：
    - 预期：理论上都会失败
    - 表现：2 家智能体应该都**只是过了 API 接口验证，没有实际做播放验证，即能否听到声音**，判断依据是都遗漏了 **swresample** 这个库，所以他们说验证通过了这句话是怎么来的，我持怀疑态度

### Python 坦克大战游戏转写任务

1. **问题背景**：坦克大战[**源码**](https://github.com/Fxy0211/TankWar)，拉取后放在 **TankGame** 目录下；游戏所需的所有贴图、音效文件均已提供，没有也不需要支持 BGM；考察坦克大战游戏是一个非常好的点，因为在大众的认知中，这就和**俄罗斯方块**一样，应该是最基本的能力了，况且现代游戏开发有那么多**游戏引擎**和**开源工具或库**
2. **问题描述**：你可以访问的工作目录为：TankGame，你的任务是把 Python 写的 TankGame 转为 C++ DirectX 写的游戏源码，转写过程中的代码功能分析、源码等，都输出到 TankGame-Qoder 下面。注意：请使用当前机器里面自带的 C++ 版本和工具，DirectX SDK 也是一样，如果没有 DirectX SDK，那么请按照顺序从 OpenGL、Vulkan、GDI、GDI+ 里面选择一个实现
3. **问题潜在难点**
  - Python 转 C++ 好比文科转理科，内存泄露等问题很容易出现，但是这部分短时间内不好验证
  - 要求使用 DirectX 的 Win32 开发，而不是开源库、商业游戏引擎，这部分大模型的训练语料本身就很少
  - 游戏是一个综合性的任务：音效、背景音乐、画面、游戏逻辑，整体的联动就是一个复杂的轻量架构
4. **个人预期与实际表现**：
  - 预期：智能体应当能在不安装额外开发工具的情况下，通过 **plan** 模式整理好完整的工作流，并完成任务
  - 表现：本次测试只有 **CodeBuddy** 胜出，**Qoder** 多次生成错误（**2 个小时都是错的，烧 Token 很快，很长时间才修改差不多**）！本次测试是唯一一次同时使用 **plan** 模式对比测试，**Qoder 此前胜出**的大概原因是因为其 **plan** 模式和普通模式的工作流差异并不大，而 **CodeBuddy** 差异明显，仅 **plan** 模式才会加入复杂工作流和前后切换验证
